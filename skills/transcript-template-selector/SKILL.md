# 逐字稿模板选择器

## 目标

先为逐字稿选择合适的纪要骨架模板，再只填充有原文依据的内容。

## 工作流

1. 读取逐字稿。
2. 判断会议类型。
3. 选择匹配的骨架模板。
4. 只抽取有证据支撑的内容。
5. 校验并删除不被支撑的内容。
6. 渲染为目标模板。

## 当前分类类型

当前仓库实际使用以下 7 类：

- `project_sync`
  适用：项目同步、进度会、里程碑跟进、上线排期、阻塞协调
- `decision_review`
  适用：方案评审、需求评审、拍板会、取舍讨论
- `issue_triage`
  适用：问题排查、故障复盘、止血和修复路径讨论
- `brainstorming`
  适用：头脑风暴、开放探索、创意发散、方向讨论
- `interview_research`
  适用：用户访谈、客户访谈、调研复盘、痛点归纳
- `universal_minutes`
  适用：复盘、部署、任务压实、协同推进等混合型或长会议，作为通用兜底模板
- `general_meeting`
  适用：普通会议、信息同步会、未命中明显特征但仍需按常规纪要输出的场景

## 分类规则

- 分类只用于选择骨架模板和调整抽取重点。
- 分类结果不能削弱任何证据规则。
- 优先判断是否存在明确主类型；如果内容混合、边界不清或主类型不明显，则退回 `universal_minutes` 或 `general_meeting`。
- `universal_minutes` 是结构化兜底模板，不是失败态；它用于承接复杂、混合、部署复盘类会议。
- `general_meeting` 是普通会议模板，适用于缺少强信号、但又不需要使用通用归纳模板的场景。

## 分类信号

可参考当前仓库中的关键词和显式模式进行判断：

- `project_sync`
  常见信号：`进度`、`阻塞`、`排期`、`里程碑`、`风险`、`负责人`、`下周`、`上线`、`已完成`、`进行中`、`下一步`、`当前阶段`
- `decision_review`
  常见信号：`决策`、`评审`、`需求评审`、`方案`、`拍板`、`通过`、`不通过`、`取舍`、`优劣`
- `issue_triage`
  常见信号：`问题`、`故障`、`排查`、`原因`、`复现`、`修复`、`影响范围`、`止血`
- `brainstorming`
  常见信号：`头脑风暴`、`脑暴`、`想法`、`创意`、`方向`、`探索`、`试试`、`开放`、`草案`、`可行性`
- `interview_research`
  常见信号：`受访`、`用户访谈`、`客户访谈`、`痛点`、`代表性原话`、`使用场景`、`体验`
- `universal_minutes`
  常见信号：`复盘`、`部署`、`总结`、`安排`、`推进`、`协同`、`目标`、`任务`
- `general_meeting`
  默认不依赖固定关键词，通常作为普通同步类或弱特征场景的承接模板

## 显式判定与兜底规则

- 如果逐字稿明确出现 `头脑风暴`，且相关信号足够强，优先判为 `brainstorming`。
- 如果逐字稿明确出现访谈指示语，如 `今天访谈的是`、`本次访谈`、`访谈对象`，优先判为 `interview_research`。
- 如果逐字稿明确出现评审指示语，如 `今天评审`、`本次评审`、`方案 A`、`方案 B`、`最终决定`、`拍板`，优先判为 `decision_review`。
- 如果会议同时命中多类特征，且没有单一主导类型，优先使用 `universal_minutes`。
- 如果会议较长、结构复杂，并同时包含复盘、部署、任务压实、协同推进等内容，优先使用 `universal_minutes`。
- 如果只出现普通同步、提醒、活动安排、录屏、群内同步等弱信号，且没有更强类型，使用 `general_meeting`。

## 骨架选择规则

- 在仍然适配逐字稿内容的前提下，优先选择最窄、最具体的模板。
- 如果没有明显主类型，则优先考虑 `universal_minutes`。
- 如果只是普通会议或弱特征场景，则使用 `general_meeting`。
- 模板结构应保持固定，生成时不要临时发明新分区。
- 最终输出必须包含：
  - `议题`
  - `结论`
  - `待办`

## 风险标签

分类与抽取时应同时感知以下风险信号：

- `speaker_missing`
  所有分段都缺少 speaker
- `speaker_partial`
  只有部分分段缺少 speaker
- `long_context`
  逐字稿很长，需考虑分块处理
- `hypothesis_heavy`
  原文大量出现 `可能`、`猜测`、`不确定`、`假设`
- `conflict_present`
  原文存在 `不同意`、`反对`、`争议`、`分歧`
- `no_clear_conclusion`
  原文缺少 `决定`、`确认`、`定下来`、`结论`、`负责`、`截止` 等明确信号
- `mixed_type`
  同时命中多类会议特征
- `use_universal_template`
  最终使用了 `universal_minutes` 作为兜底模板

这些风险标签不能直接改变事实抽取结果，但应影响：

- 是否采用更保守的表述
- 是否回退到通用模板
- 是否更严格地删除弱结论和弱待办

## 硬约束

- 不得编造 `seg_id`。
- 不得编造 `owner`。
- 不得编造 `due`。
- 不得编造结论或共识。
- 每个非空字段都必须带有 evidence。
- 每条待办任务都必须带有 evidence。
- 如果 `owner` 不是逐字稿里真实出现的 speaker，则留空。
- 如果 `due` 不是原文明确给出的时间，则留空。
- 如果某个议题没有明确结论，应输出“未形成明确结论”或等价的无结论表达，不能写成已达成一致。
- 如果证据不足或证据缺失，直接删除该项。

## 长逐字稿处理

- 长逐字稿必要时先切块。
- 先按块抽取，再统一汇总。
- 汇总时只能复用各块结果中已经出现过的值和 evidence，不能在汇总阶段补新事实。

## 输出纪律

- 内部优先使用结构化 JSON。
- 用户看到的模板内容只能从结构化层渲染出来。
- 字段顺序保持稳定。
- 不要为了语言润色牺牲真实性。

## 优先优化目标

- 模板匹配准确
- 证据可追溯
- 分类稳定
- 不幻觉责任人、时间、数字和决策
